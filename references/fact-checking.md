# 事实核对四道（N1-N4）详解

> 核心：引用任何开源项目的"爆款叙事"之前，先过四道核对。**核对的产出是一页「事实核对表」，它是后面三层迭代的输入——基于未核对的叙事做迭代计划 = 在话术上盖楼。**

## N1：Star 数 = 曲线上的点，不是快照

### 为什么单点 Star 数不可信

```
内容号话术的生成机制：
  截图时刻的 Star 数 + "一夜爆火"叙事 → 读者脑补"现在更火、值得立刻上"
  但单点数字丢失了两个关键信息：
  1. 斜率（增长速度：是持续累积还是事件尖峰）
  2. 时间戳（这个数字是多久以前的）
  42.9K 可能是"三周前的 42.9K"，也可能是"三个月前的 42.9K"——
  后者的话，现在可能已经 47K+，也可能增长已经停了
```

### 轨迹数据从哪找（按可信度排序）

```
1. 仓库自身的版本 tag + release 日期（最硬）：
   git ls-remote --tags / GitHub releases 页
   每个 tag 的日期 = 一个时间点锚（Star 数不一定标，但版本号是锚）
2. 第三方目录/统计的同步数据（次硬）：
   原文例：32.9k(v2.6.0 前后)→36.3k→39.4k→42.5k→47.1k(2026-09)
   注意：第三方同步有延迟且口径不一，只用于"方向+量级"，不用于精确值
3. 你自己定期拉取（最可靠但需要持续）：
   gh api repos/<owner>/<repo> --jq '.stargazers_count' 每周存一个点
   存 3 个点以上才有斜率；1 个点 = 快照，无信息
判定规则：
  ≥3 个时间点且单调递增 → "持续累积增长"（真实趋势，可放心引用，带时间戳）
  有尖峰（某段陡增）→ 标注事件（发推/被大 V 引用），尖峰后斜率回落 = 话术高发区
  只有 1 个点 → 标"仅快照"，按话术风险降级处理（引用必须带"截至 X 日"）
```

### 核对表写法（N1 行）

```markdown
N1 Star 轨迹：
  锚点：v2.6.0 前后 ≈32.9k → 36.3k → 39.4k → 42.5k → 47.1k（2026-09 第三方同步）
  斜率判断：持续数月累积增长（非事件尖峰）
  结论：宣传的"42.9K 一夜爆火"= 曲线中点+话术；当前实际更高，引用用"47.1k @2026-09"
```

## N2："只挑了最吸睛的"偏差

### 偏差机制

```
宣传清单（图/文/推）的挑选逻辑 = 最新 + 最吸睛 + 最好讲
  → 挑出来的永远是 marketing-council（12 位传奇营销人，故事性强）
  → 不会被挑出来的是 CRO 审计、文案改写、付费投放这些" boring 但天天用"的
  后果：你以为库 = 4 个 Skill，实际 = 47 个（v2.8.0）现 v2.9.0
  覆盖面从 CRO/文案/付费投放到 RevOps/定价——你的真实需求很可能在
  那 43 个"没被宣传"的里面
```

### 全量清单筛查法

```
步骤：
1. 拉全量：读仓库 SKILL 目录清单（或 README 的完整列表），列全 N 个
2. 按你的场景打标签：每个 Skill 标 [直接相关/间接相关/无关]
   判据：这个 Skill 的"触发条件"字段（工程范式的第一个字段）
   是否描述了你日常会出现的场景——不是看名字像不像
3. 筛出工作清单：直接相关 → 首跑候选（进 L1）；间接相关 → 备选；无关 → 忽略
4. 对账：宣传清单的 M 个 ⊆ 全量清单的 N 个？（不 ⊆ = 宣传里有幻觉，回查 N3）
核对表写法：
  N2 实际规模：47 个 Skill @ v2.8.0（现 v2.9.0）；宣传清单 4 个（最新最吸睛）；
  与我的场景相关：cro / seo-audit / marketing-loops / 定价类 1 个（共 4 个进 L1 候选）
```

## N3：模拟/人格类 Skill 的护栏要读原文

### 为什么必须读原文

```
"marketing-council"这类 Skill 的危险面不在"输出质量"，在"输出被误当真人背书"：
  读者/用户可能把模拟输出当成 Godin 本人会说的话 → 对外引用 = 虚假背书
  护栏（输出标注模拟/禁编造引语/不暗示真人背书）是 Skill 自带的"免责声明"，
  但免责声明不写进你的使用流程 = 没人执行 = 护栏形同虚设
读原文的动作：
  1. 定位：SKILL.md 里的"约束/护栏/禁止"段落（通常在 frontmatter 或文档末尾）
  2. 摘录：逐条抄进核对表（不抄 = 没读，凭印象会漏"不暗示在世顾问"这种细节）
  3. 翻译成你的执行规则：每条护栏 → 一条"我使用时怎么做"（见下例）
```

### 护栏原文 → 执行规则的翻译例

```
护栏原文（marketingskills/council）：
  "输出必须标注为模拟"
  "禁止编造引语"
  "不暗示真人背书在世顾问"
翻译成执行规则（写进你的 SOP）：
  1. 每次引用 council 输出，落款处带"[模拟顾问团输出，非本人观点]"
  2. council 输出里出现"某人说：…"格式的句子 → 逐条核对是否有 N2 级别的
     可溯源出处，没有 → 删除该句（宁可输出变短）
  3. 对外材料里 council 的结论只能以"我们用了一套多视角推演，结论是…"表述，
     不能以"Ogilvy 会认为…"表述
验收：抽 3 条历史输出，3/3 符合上述三条 = 护栏在执行；任一条不符 = 补流程
```

## N4：第三方评测点名的真问题

### 为什么评测限制项 = 必做项

```
评测者用"生产落地"标准看，点名的限制通常是你自用阶段感觉不到、
但上生产就爆的问题：
  原文两点：
  a. "Skill 定义很固执，不会自动适配你现有的 SEO/RevOps 流程和工具栈"
     → 翻译：Skill 假设了一套默认流程，你的流程不一样时它不自动让步
     → 迭代含义：L2 定制不是"锦上添花"，是"生产落地的前置"（必做）
  b. "安全扫描 2/3 通过"
     → 翻译：有一类安全项没过（具体是什么看评测原文）
     → 迭代含义：上生产前必须查没过的那项影响什么 + 你是否有对应控制
     （有控制 = 记录豁免理由；没控制 = 不上生产）
转迭代计划的映射：
  评测限制 a → L2 动作 c（接真实数据时，先跑通你的流程再让 Skill 套进来）
  评测限制 b → L2 动作 d（veto list 里补安全项）+ 上线前复查
```

### 核对表 N4 行写法

```markdown
N4 评测点名的限制：
  a. Skill 不自适现有流程/工具栈 → 转 L2-c（先跑通我的流程）【必做】
  b. 安全扫描 2/3 → 未过项：<查评测原文具体项>；我的控制：<有/无>；
     无控制时上线门槛：<条件>
结论：有条件进入迭代（条件：N4-b 的未过项在 L2-d 中处置完毕）
```

## 核对表模板（N1-N4 汇总）

```markdown
# 事实核对表 <库名> <日期>
N1 Star 轨迹：<≥3 锚点或"仅快照">；斜率：<累积/尖峰/未知>；
   引用规范：裸数字禁用，必须"数字 @时间点"
N2 实际规模：<N 个 @ 版本>；宣传 <M 个>；与我的场景相关：<清单>
N3 模拟类护栏原文：<逐条摘录>（无 = N/A）→ 执行规则：<翻译后的 3 条>
N4 评测限制：<列表> → 转迭代必做项：<编号映射>
结论：放心进入 / 有条件进入（条件：__）/ 不建议进入（原因：__）
```

**"有条件进入"的处置**：条件全部写进迭代计划的第一行（不是写在核对表里就完了——核对表是判断，迭代计划是执行，条件必须从判断流进执行）。
